# Blender 节点图转译复刻计划

> **一句话**：不再用"挑一个通用卡通着色器再调参数"的方式逼近 `.blend` 渲染预设，改为把预设的节点图**逐节点转译**成 HLSL。目标是数学精确复刻，不是视觉近似。
>
> 本文写于 2026-09-10，取代 `2026-06-22-liltoon-npr-render.md`（该计划连同其全部产物已归档到分支 `archive/liltoon-npr-tuning`）。

**这份文档记的是「为什么这么做」和「实测出了什么」，按阶段追加。想知道「怎么跑」请看
`Tools/PmxPipeline/README.md`。** 各阶段的验收数值按时间顺序排在下方 Phase 小节里，最新
的一次全量结果在 Phase 3.6。

## Goal

给定「PMX 角色模型 + 配套 `.blend` 渲染预设」，离线生成 `.me`，使其在本软件中的渲染结果与在 Blender 中看到的一致。

先跑通「丽塔」一个角色，但**架构按通用管线设计**——转译器是一次性投入，为单角色写死不会更省事，而丽塔恰好是已知四个预设中最复杂的一个（唯一用到程序化噪声、唯一需要 6 张 LUT）。

## 为什么之前的路线必然失败（根因，勿重蹈）

两条独立的原因，任何一条都足以致命：

1. **导出环节从第一步就丢了算法。** `Tools/PmxPipeline/dump_render_preset.py` 遍历节点树时**从不记录 `node_tree.links`**，只按关键词（`"shade"`/`"高光"`/`"outline"` 等）猜测插槽含义，塞进一个 UTS2 形状的扁平字典。节点图的拓扑结构完全没有被导出过。之后所有工作都建立在这份有损摘要上。
2. **拟合维度不足。** 目标是一张 712 个计算节点的图，而 UTS2 / lilToon 只暴露二十几个可调项。参数拟合在理论上就无法收敛——这不是"没调好"，是无解。ADR-0010 记录的 UTS2 死路、以及后来 lilToon 迭代到 Phase 2.18 仍"总差一点"，都是同一个原因。

## 关键发现：这套预设是无光照纯函数

**这是整个新方案成立的前提，已实测确认。**

材质把 Color 直接接进 `Material Output ▸ Surface`。实测该写法与 Emission 输出**逐位相同**（`probe_raw_*.png` 与 `probe_emission_*.png` 哈希一致），而 Diffuse BSDF 在无灯环境下渲染为纯黑。预设文件里唯一的灯是 `energy = 0.0` 的太阳，World 为空。

光照是节点图自己伪造的——有个组就叫 `虚拟日光`，实质是：

```
ndl = dot(SUN * 2.8, N_world)
t   = saturate((ndl + 1) * 0.5)
s   = saturate(t * 0.5 + 0.5) ^ 2
ao  = (lightmap.g > 0.25) ? 1.0 : 0.5
out = s * ao
```

对四个预设**每一棵树**做全量 `bl_idname` 枚举确认：`ShaderToRGB`、`AmbientOcclusion`、`Bevel`、`LightPath`、`LayerWeight`、`Fresnel`、`BsdfPrincipled`、`VertexColor` 均为 **0 次**；四个 `worlds` 字典全为空。128 个材质中 **124 个是纯函数**，其余 4 个是每个预设里的 `表情` 材质（mmd_tools 导入残留，作者未套预设，在 energy=0 下求值为黑）。

**因此整个渲染是一个可以被完整搬走的片元函数**：输入是贴图、UV、法线、视线方向、三个方向向量；输出是最终颜色。不依赖 Blender 的光照引擎、阴影贴图、全局光照或任何屏幕空间缓冲。

## Architecture

```
渲染预设.blend ──[export_blender_graph.py]──> 节点图 JSON
                                                  │
                                        [转译器] ─┼─> HLSL 着色器
                                                  ├─> LUT 贴图（ColorRamp / RGB Curves / 视图变换）
                                                  └─> uniform 清单
PMX ──[现有 PmxPipeline]──> 网格/骨骼/BlendShape/物理
                              │
                    [描边烘焙] └──> 外壳子网格（焊接法线 + 权重 + 描边色烤进顶点流）
                                                  │
                                            [ExportMe] ──> .me
                                                  │
                              [差分验收] Blender 无头渲染 vs Unity 渲染 → 像素差异
```

**只替换材质环节。** `Assets/Editor/PmxPipeline/` 的 PMX 解析、网格构建、Humanoid、物理、`.me` 打包全部照用，`PmxStyleConfig.materialProfile` 是现成接入点。UTS2 映射保留作兜底。

## 已核实的事实清单（勿重复推导）

### 预设的应用流程

由配套插件 `模型预设导入.py` 完成（副本存于 `Docs/RenderPreset/vendor/`，原件在本机 Blender 的 `scripts/addons/` 下）。用户操作是：导入 PMX → 物体模式选中模型 → N 键侧边栏 → RenderTools ▸ 导入预设 → 选 `.blend`。

插件实际做的事：

| 步骤 | 行为 |
|---|---|
| 材质配对 | 默认「剪去后缀」模式，把现有材质改名为 `actual_*`，按名字换上预设材质。**撞名问题由插件自动处理，无需手工重指材质槽** |
| 节点组导入 | 导入全部 node_groups；对每个 `users == 0` 的几何节点组，把输出接口的 `default_attribute_name` 设为接口名，并自动添加 NODES 修改器 |
| 对象链接 | 把预设里的 `灯光` 和 `面部定位` 链接进场景 |
| **面部定位绑骨** | **自动 parent 到骨骼 `頭`**（`parent_type='BONE'`），并做矩阵补偿。**所以脸部 SDF 阴影确实跟随头部转动** |
| **场景效果** | 见下，这一条极易被忽略 |

### 场景效果：真正生效的设置来自插件，不是 `.blend`

```python
scene.eevee.use_bloom        = True
scene.eevee.bloom_intensity  = 0.08
scene.eevee.bloom_color      = hex_to_rgb(0xFFE4D9)   # 暖白
scene.view_settings.view_transform = 'Filmic'
scene.view_settings.look           = 'High Contrast'
```

> **陷阱（本项目已踩过一次）**：`渲染预设.blend` 是**没有场景的纯材质库**，它内部存的那份 scene 设置（`use_bloom=False`、`look='None'`）是**死数据**，读它会得到错误结论。真正生效的是插件写进用户文件的上述设置。判断"什么设置在生效"必须以插件为准。

### 视图变换曲线（实测）

`Filmic` + `High Contrast`，逐通道独立（四组含高饱和与 HDR 值的测试，通道间偏差全为 `0.00000`）→ **可以烤成一张一维 LUT，在片元着色器末端逐像素套用，alpha 不受影响**。

| 线性输入 | look=None | **look=High Contrast（实际生效）** |
|---|---|---|
| 0.01 | 0.10111 | **0.05127** |
| 0.04 | 0.24117 | **0.17894** |
| 0.18 | 0.50021 | **0.50028** |
| 0.50 | 0.69496 | **0.74499** |
| 1.00 | 0.80723 | **0.86294** |
| 8.00 | 0.98315 | **0.99292** |

注意 **线性 1.0 只映射到 0.863，Blender 里画面永远不会出现纯白**。Unity 不做这层变换会直接烧成白色。历史上反复出现的"惨白"判定，有一部分根因在此，而不全是材质调坏了。

### 着色器需要的外部输入（只有三个）

由几何节点修改器写成网格命名属性，实测全网格恒定 → **在 Unity 里就是三个 `float3` uniform**：

| Uniform | 来源 | 默认值（Blender 轴） | 语义 |
|---|---|---|---|
| `_SunDir` | `灯光` 对象局部 +Z 的世界方向 | `(0, -0.866025, 0.5)` | 表面指向光源 |
| `_HeadBack` | `面部定位` 局部 +Y 的世界方向（属性名 `FRONT`） | `(0, 1, 0)` | **头部背向，不是面朝方向** |
| `_HeadRight` | `面部定位` 局部 +X 的世界方向（属性名 `RIGHT`） | `(1, 0, 0)` | 决定 SDF 左右翻转 |

后两个由头骨 `頭` 驱动。`FRONT` 的符号语义已实测核对：丽塔脸部材质面积加权平均法线为 `(0, -0.8955, -0.4451)`，模型面朝 Blender −Y，故 `FRONT` 指头后方。光在正面时 `dot(FRONT,SUN) ≈ -0.866` → 阈值 ≈0.067 → 脸几乎全亮，行为正确。

属性缺失时 Attribute 节点返回 `(0,0,0)`，会让所有点积退化为 0，**没有可用兜底**。

### 脸部 SDF 数据流

```
flip      = step(0, dot(SUN, RIGHT))
uv'.x     = flip ? uv.x : 1.0 - uv.x          // Blender 用 extension=REPEAT 的 frac(-u) 实现
facemap   = tex2D(Facemap, uv')                // 采样方式见「坑」一节
threshold = dot(FRONT, SUN) * 0.5 + 0.5
SDF       = (luma709(facemap) > threshold) ? 1 : 0
```

### 描边

几何节点做的实体化外壳，**不是着色器 pass**：

```
offset = N_welded × 0.0012 × W
```

- `N_welded` = 按 `1e-4` 距离**焊接之后重算**的顶点法线。实测 14132 个外壳顶点：与焊接后法线吻合中位数 `1.0000`（92.9% 完全吻合），与原网格法线仅 `0.9863`（44.9%）。**`Merge by Distance` 在这里的职责就是平滑法线**，把 UV 缝/材质缝上分裂的顶点焊回去，否则外壳会在缝上裂开（丽塔 26366 → 14346 点，焊掉 45%）。
- `0.0012` 是对象局部单位的全局常量，模型世界包围盒高 `1.5663`，即身高的 **0.0766%**。**没有任何缩放补偿**，Unity 导入若换了单位缩放必须同比换算。
- `W` = 手绘遮罩（头发用 `hairmask`，脸用 `描边遮罩`，均打包在 `.blend` 内）× 用户权重。两张图实测 100% 像素 `r==g==b`，约 92% 为 1.0、3~5% 为 0.0，其余是手绘过渡带。
- 部位划分靠 4 个 `Set Material` 串联，采用**顺序消耗**语义（`Material Selection` 在它所作用的那份几何上重新求值，已用最小用例实测验证）。丽塔实测：`edge_clothes 23748` / `edge_hair 2446` / `edge_skin 1570` 面，后两者恰等于 `头发` 和 `脸` 材质的面数。
- 颜色：`edge_skin` 与 `edge_hair` 是常量；`edge_clothes` 按 **Body_LightMap 的 alpha 通道**做五档 one-hot 查表（丝绸 0.90 / 金属 0.60 / 布料 0.35 / 皮革 0.20 / 皮肤 0.05，容差均 0.05）。
- `Flip Faces` + 四个 `edge_*` 材质全部 `use_backface_culling = True` = 标准反向外壳。
- 外壳规模：27764 面 / 14346 点，继承 `UVMap` 与全部 661 个骨骼顶点组，可正常蒙皮。

### 对模型侧的硬要求只有两条

1. 一套名为 `UVMap` 的 UV
2. 材质名与预设一致

丽塔 PMX 实测全部满足：PMX 2.0、`additional_uv = 0`、mmd_tools 导入后 `uv_layers = ['UVMap']`、26 个材质名 1:1 全对上。

**不需要顶点色**——这一点推翻了 ADR-0009 的适用范围：当年 HoyoToon 因 PMX 缺顶点色而失败的结论本身没错，但那是 HoyoToon 的需求，**这套 `.blend` 预设从不读顶点色**（四个预设 `VERTEX_COLOR` 节点数为 0）。

另外核实：预设**完全没有使用** PMX 的 `edge_color` / `edge_size` / 逐顶点 `edge_scale`。网格上存在 `mmd_edge_scale` 属性但无任何节点引用。

| 项目 | 数量 |
|---|---|
| 参与运算的节点（四预设合计） | 712 |
| 节点求值函数（类型 × 属性组合去重） | 50（排除 `表情` 的 BSDF 则 48） |
| 节点组实现（按结构去重） | **41** |
| 需要烘焙的 LUT | 7（ColorRamp 6 个全在丽塔 + RGB Curves 1 个四预设共用） |

> **别被"四个预设共享 27 个同名组"误导**——那只在名字层面成立。做名字无关的结构比对后，**9 个同名组在不同预设里结构不同**（例：`描边权重` 在丽塔是 11 节点/10 连线，在灯是 31 节点/30 连线）。实际要落地 41 份实现。
>
> **这正是必须写转译器而非手写着色器的最强论据**：手写意味着 41 份人工劳动且每换一个角色重来；转译器只是多跑几遍。

已确认的死代码，不计入工作量：`昼夜控制`（夜间分支被常量焊死，且唯一使用点无出边）、`法线贴图转换`、`matcap`（非 hair 版）、`Geometry Nodes` 的着色器侧——四个预设中均不可达。

## 必须写进转译器的坑

每一条都是"不知道就会静默出错、且极难定位"的类型。

1. **隐式类型转换用 Rec.709 亮度。** Blender 把 Color 转 Float 用 `0.2126r + 0.7152g + 0.0722b`，不是算术平均（实测 `RGB(0.1,0.6,0.9)` → `0.515360`，算术平均应为 `0.533333`）。可达连线里有 **23 条 `RGBA→VALUE`**，用错会全线偏色。
2. **`ShaderNodeMix` 的残留连线。** 有 **8 条连线**（每预设 2 条，**全在 `SDF` 组**）挂在非活动 `data_type` 的 `A_Float`/`B_Float` 插槽上，是作者切换过类型的残留。Blender 求值只看活动变体，转译器必须按 `data_type=RGBA` 只取 `A_Color`/`B_Color`/`Result_Color`。读错的表现是**人脸阴影完全不对**。
3. **人脸 SDF 图的采样方式是 `Smart`** → EEVEE 走 `texture_bicubic`（4 抽头 B 样条），而其输出直接进一个 CONSTANT ramp 做硬阈值（阈值因预设而异：0.3417 / 0.325 / 0.315）。用双线性会让阴影分界线的形状和位置可见偏移。**这是全图唯一一处采样滤波影响外观的地方。**
4. **ColorRamp / RGB Curves 必须按 EEVEE 的方式烤 257 项表。** EEVEE 自身实现为 `sampler_offset = 0.5/257.0`、`sampler_scale = 1.0 - 1.0/257.0`。照做即逐位一致；`257`（`CM_TABLE + 1`）是写死的魔数。2 停 CONSTANT 的 ramp 走 `valtorgb_opti_constant`，内联 `fac > edge ? c2 : c1` 即精确，不占 LUT。
5. **描边颜色查表的容差极窄。** 实测 Body_LightMap alpha 的实际取值为 `0.05 / 0.18 / 0.36 / 0.59 / 0.85`，其中 `0.85` 距档位中心 `0.90` 只有 `0.049`，而容差是 `0.05`。运行时若用双线性 + mipmap 采样，跨材质 ID 边界的混合值会掉出所有档位变成黑边。**对策：离线把描边颜色逐顶点烤成顶点色**，既消隐患又省一次采样。
6. **描边导出陷阱。** 外壳经 `Geometry to Instance` 变成实例，`bpy.data.meshes.new_from_object()` 和「转换为网格」**都会静默丢掉整个外壳**（输出仍是 30408 面、无 `edge_*` 材质）。必须先 `Realize Instances`。
7. **UV 缝上的遮罩采样是按平均 UV 取的。** `Capture Attribute` 在 POINT 域求值而 `UVMap` 是 CORNER 域，Blender 做算术平均（实测同一顶点两角 u=0.1 与 0.9 → 捕捉到 0.5000）。这是原作固有行为，移植时要**主动决定复刻还是修正**。
8. **两张描边遮罩标了 sRGB**，而几何节点的 Image Texture 读的是色彩管理后的 scene-linear 缓冲，手绘中灰读出来约 0.216 而非 0.5。近二值的遮罩下影响很小，但要逐位一致就得复刻。

#### 建立起来的对齐保证

- **坐标映射是推导出来的，不是调出来的**：mmd_tools 用 `Vector(pv.co).xzy * 0.08`，
  Unity 侧 `PmxMeshBuilder.Conv` 用 `(-px, py, -pz) * 0.08`，消去 PMX 坐标得
  `U = (-B.x, B.z, -B.y)`。yaw 两边通用。
- **取景不各算各的**：Unity 侧直接读 Blender 报告里的 `cam` 段。
- **姿势对齐**：`PmxHumanoid` 会在捕获 bindposes 之后把手臂掰成 T 姿势（Humanoid
  Avatar 需要），prefab 因此停在 T 姿势。渲染时把骨骼写回 bindpose 即精确还原 PMX
  原始姿势，prefab 本身不动。
- **背景不进统计**：Blender 的世界背景同样要过 Filmic（给 808080 渲出来是 8C8C8C）。
  两边都用透明背景渲，统计只在 alpha 轮廓交集内做。

1. **Reroute 断链（严重）。** `graph_ir.py` 按名字找 Reroute 的输入插槽 `Input`，

#### 程序化纹理（2026-09-19 补齐）

`头发` 的 Noise 与 `胸衣` 的 Voronoi 一开始是占位常量，后来连同 `Generated` 坐标
一起实现了：Blender 的 Jenkins lookup3 整数哈希、Perlin 噪声（含 `noise_scale3`
= 0.9820 这个系数）、fractal_noise、Voronoi F1 3D 欧氏距离。两点值得记：

- 浮点版哈希吃的是**浮点数的位模式**（`asuint`），不是取整后的格点，写错就是另一张图。
- `Generated` 必须先把 Unity 局部坐标转回 Blender 物体空间（`B = (-Ux, -Uz, Uy)`）
  再按包围盒归一化，轴错了花纹方向全变。包围盒由 Unity 侧从网格 bounds 换算后写进
  uniform，实测两边尺寸完全一致：`(1.0890, 0.3013, 1.5663)`。

补齐后逐像素 ΔE 几乎没动（`胸衣` 2.94 → 3.10）——高频随机花纹本来就不可能逐点对上，
但**肉眼观感对上了**，这正是坑 9 讲的那件事。

#### 架构决定：Python 出着色器，Unity 只负责绑定

转译器写在 Python 侧（`Tools/PmxPipeline/transpile.py`），产出：

```
Assets/Generated/PmxTranspiled/<角色>/shaders/M??.shader   每材质一个（已 gitignore）
Assets/Generated/PmxTranspiled/<角色>/<角色>.bindings.json 装配清单 + LUT 浮点数据
Build/RenderPreset/images/<角色>/                          从 .blend 解包出的 19 张贴图
```

落地时与原设想的三处偏差：

- **一材质一着色器**，不是一个大着色器。常量直接内联成字面量，贴图属性按需声明，
  没有 uber-shader 的分支与变体问题。30 个无光照着色器的编译开销可以忽略。
- **节点求值库内联进每个着色器**而不是 `.cginc`：生成物落在带中文名的目录下，
  相对 include 路径多一层不确定性，而库只有两百多行。
- **LUT 走 JSON 里的浮点数 + 运行时建 `RGBAFloat` 贴图**，不烤 PNG：表值在线性域，
  8 位量化在 Filmic 曲线最陡的暗部会放大成可见色差，16 位 PNG 又要额外约定导入设置。

Unity 侧只读 `bindings.json` 建材质，不参与图分析。这样分工的理由：

- 图分析与代码生成迭代频繁，Python 改完立刻能跑；放 Unity 里每次都要等编译。
- 节点图 JSON 本来就是 Python（Blender）产出的，同一侧处理省一次格式往返。
- Unity 侧的职责收窄成"按清单装配"，正好接进既有的 `materialProfile` 扩展点
  （Phase 4）。

**`bindings.json` 必须带混合状态**，不能只有贴图和颜色——`眼睛2` 那个 bug 的一半
原因就是队列与混合模式错了（见上方 Phase 2 核验项）。

#### 节点类型清单（已全部实现）

由 `graph_ir.py` 按需展开后实测得出（丽塔全材质，`graph_ir.py <graph.json>` 可随时重跑）：

```
MATH 274   MIX 188   IMPLICIT_CONV 137   VECT_MATH 86   VALTORGB 82
TEX_IMAGE 63   ATTRIBUTE 48   MAP_RANGE 40   NEW_GEOMETRY 32   HUE_SAT 31
SEPARATE_COLOR 31   CURVE_RGB 24   NORMAL_MAP 15   MIX_RGB 6   MAPPING 3

```

BSDF_* 与 MIX_SHADER **全部来自 `表情` 一个材质**——它走 mmd_tools 的
`MMDShaderDev`（真 BSDF），是预设作者唯一没做风格化的材质。

闭包模型只用「辐射 + 透射」两项就覆盖了这四种节点，并与 EEVEE 的合成方式一致：
`alpha = 1 - avg(transmittance)`、`RGB = radiance`。两条实测探针为它背书：

- `Color` 直连 Surface，四种 blend_method 下输出 alpha **恒为 1**——颜色的 alpha
  **不会**变成材质透明度（这个否定结论同样重要，它排除了「眼部细条要靠贴图 alpha
  抠形」的猜想）。
- 纯 Transparent BSDF（Color = 0.2724 灰）单独渲：RGB=0、alpha=0.7294；压在白色自
  发光面前：0.5569 = sRGB(0.272394 × 1.0)。即透射项是**乘在背后颜色上**的。

由此也定出一处待办：Unity 侧对 BLEND 材质用的是显示域混合，而 EEVEE 是**线性域合成
后再过视图变换**。要彻底一致就得渲到离屏线性缓冲、末端统一做一次变换——这与 bloom
的做法是同一件事，一并放进 Phase 2.5。

#### bloom 的增益必须标定，不能直接用 intensity

EEVEE 的 `bloom_intensity` **不是**「辉光能量占比」——多级金字塔累加本身会放大数倍。
用 `Tools/PmxPipeline/probe_bloom_kernel.py` 实测（黑底上 16px 方块、发光强度 10、
1024²）：

```
源能量 2560.0   辉光能量 1245.7   占比 0.48659
过阈值后的源能量 = 2560 × 0.92 = 2355.2 → 金字塔放大 = 0.5289 / 0.08 = 6.61 倍
```

本实现（8 级、13 抽头降采样 + 9 抽头 tent 上采样）实测放大 **8.9035** 倍，于是
`MEPostCompose.AccumulationGain = 6.61 / 8.9035 = 0.7424`。改这个数之前先重跑探针。

径向剖面还确认了核的形状：r 从 20 到 180 每个环的能量几乎恒定（≈50），即 1/r² 衰减，
正是多尺度累加该有的重尾。

另一条实测结论：**Blender 的 bloom 不改 alpha**。带 bloom 的基准图里轮廓外有 314456
个像素 RGB 非零而 alpha 仍为 0，半透明像素数与不带 bloom 时一模一样（8828）。所以
合成 pass 里 alpha 原样透传即可。要让辉光在分层窗口里真的看得见，得**主动**把 alpha
一起外扩——那是有意偏离 Blender 的决定，留到 Phase 4。

#### 坑 9：Blender 对着色超采样，Unity 的 MSAA 不会

`taa_render_samples = 64` 是对**着色**做 64 次抖动采样；Unity 的 MSAA 只对几何边缘
多采样，片元着色每像素仍只算一次。对程序化纹理这类高频内容，表现是「细密低对比的
尘点」对「稀疏高对比的色点」——看起来像算错了，其实是采样率不同。

对策：渲到 `res × ssaa` 再逐级二分下采样（双线性正好等于 2×2 盒式平均），且必须在
**线性域**做，与 Blender 累加样本的域一致。默认 `-ssaa 4`。开了之后 `胸衣` 的细闪
密度与 Blender 肉眼一致，`口腔` 从 ΔE 18.27 掉到 10.60、`鞋子` 5.20 → 2.72。

#### 做法改了：不重写算法，直接搬 Blender 算好的外壳

原计划是在 Unity 侧重写整套（删除排除集 → 焊接 → 重算法线 → 采样遮罩 → 划分材质）。
实际没这么做——那等于把四处实现细节各赌一次：Merge by Distance 的合并语义、Blender
的法线加权方式、遮罩在 UV 缝上的平均取值（坑 7）、三个 `Set Material` 的顺序消耗语义。
任何一条不一致都会在轮廓上留缝，且极难定位。

改成让 Blender 自己算，只把结果搬走。关键手法是**求值两次**：

| 描边权重 | 得到 |
|---|---|
| 0 | 焊接后、未外扩的位置 —— 用 KD 树对回基础顶点，得到焊接组 |
| 1（原值） | 真正的外壳位置 / 法线 / UV / 三角形 / 材质划分 |

外壳**不继承顶点组**（实测求值后网格的 `vertices[i].groups` 是空的），所以骨骼权重
与 BlendShape 增量只能靠焊接组从基础网格推：权重逐骨骼相加后取前 4 个重新归一化，
增量取平均。取平均而不是「挑最近的那个顶点」——描边顶点落在缝上时两侧可能绑在不同
骨骼上，挑一个会让描边动起来时从缝里甩出去。

实测数据（丽塔）：外壳 14346 顶点 / 27764 面，`edge_clothes 23748` /
`edge_hair 2446` / `edge_skin 1570` 面（`edge_clothes2` 0 面），最大外扩 0.001200、
均值 0.001169、184 个顶点被遮罩压成 0——与事先测到的全部对上。焊接组共 24342 条
引用，平均每个外壳顶点来自 1.70 个基础顶点。

描边颜色没有烤进顶点色：`edge_*` 四个材质本身就在转译范围内（`edge_hair` 是常量、
`edge_clothes` 按 UV 采 Body_LightMap 的 alpha 查表），直接用转译出的着色器即可，
与 Blender 的求值时机一致。坑 5 担心的「跨档位混出黑边」没有出现。

#### 两处必须注意的绕序/剔除

1. **绕序要翻一次。** Blender→Unity 是行列式 −1 的映射（右手变左手），外壳三角形
   `(a,b,c)` 要写成 `(a,c,b)`，否则外壳正反面整个反过来，配上 `Cull Back` 就是
   「一根描边都看不见」。
2. **材质 ID 通道必须跟着真实材质剔除。** `IdPass.shader` 原本写死 `Cull Off`
   （PMX 的头发片、裙摆是单层面片，剔除会在 ID 图上留洞），但描边是**反向外壳**
   ——双面绘制时它会把整个身体盖住，ID 图上 11 万像素被标成 `edge_clothes`，逐材质
   统计全废。改法：转译着色器把 `_Cull` 暴露成属性，ID 通道照抄过去。

#### 尚未接进主管线

Phase 3 初期外壳只在 `MERefRenderer` 渲染时并入。2026-09-22 的独立导出工具已将这一步
接入 `PmxMeshBuilder`，描边写回网格资产并进入 `.me`；见 Phase 4 与 ADR-0013。

### Phase 3.5：跨角色验证（2026-09-22）

丽塔一个角色跑通不等于流程成立——预设是同一套节点组，但每个角色接线不同、材质
设置不同。拿另外两个角色（`大格蕾修`、`灯`）原样跑了一遍全流程：导出节点图 → 烘
描边外壳 → 转译 → 四视角差分。

| 角色 | 材质 | front | three_quarter | right | back |
|---|---|---|---|---|---|
| 特工丽塔 | 30/30 | 0.9980 / 1.84 | 0.9978 / 1.82 | 0.9980 / 1.72 | 0.9980 / 1.63 |
| 大格蕾修 | 34/34 | 0.9988 / 2.52 | 0.9987 / 2.50 | 0.9987 / 2.59 | 0.9989 / 2.00 |
| 灯 | 31/31 | 0.9983 / 1.80 | 0.9982 / 1.68 | 0.9981 / 1.62 | 0.9983 / 1.08 |

（格式为「轮廓 IoU / 交集内平均 ΔE76」。对照：Phase 0 的 UTS2 基线是 0.9677 / 11.00。）

流程本身没有改动就跑通了，但暴露出三个只有换角色才会碰到的缺陷，全部修掉：

**1. 四个未实现的节点类型。** `VALUE` / `RGB`（纯常量节点，常量存在**输出**插槽的
`default_value` 上，IR 之前只留了输出插槽的类型、把默认值丢了）、`INVERT`、
`COMBINE_COLOR`。三个材质因此整条链断掉。补齐后 34/34、31/31，零未支持。

**2. 没有复现 EEVEE 的「Show Backface」。** 材质关掉这个开关
（`show_transparent_back = False`）时，EEVEE 会给它加一遍**深度预通道**，效果是每
个像素只有最靠前的那一层被着色。我们的 Unity 侧是普通的 `ZWrite Off` 透明，所有
层都画——灯的 `长头发1` 于是在本该被挡住的地方透出一片半透明鬼影，肉眼可见。
修法是在生成的着色器里加一个 `ZWrite On / ColorMask 0 / Blend Off` 的前置 Pass，
用同一份 alpha 做 `clip`（完全透明的片元不能写深度，否则会把后面本该可见的层抹
掉）。`长头发1` 的 ΔE 从 5.44 / P95 29.17 降到 **0.88 / P95 1.96**，灯整体 2.32 →
1.80。丽塔只有两个小面积 BLEND 材质，这个缺陷一直没被触发。

**3. 正交相机下的视线向量算错了。** EEVEE 的 `cameraVec()` 在透视下返回「表面指向
相机位置」，**在正交下返回常量的相机朝向**。基准图用的就是正交相机，我们却一直用
透视公式，画面边缘视线偏出约 5°。漫反射完全看不出来，但金属件走的是布林冯高光
（高次幂 + `GREATER_THAN` 硬阈值），边界会被这点角度推着跑。改成按
`unity_OrthoParams.w` 分支后，大格蕾修的 `衣饰铁` 5.49 → 5.16、`裙带铁` 4.55 →
4.42、`袖子铁` 3.15 → 3.02。

#### 剩下的差异查清了，不是 bug

- **金属件（所有「铁」材质，ΔE 3～5）**：均值差只有 ±2/255，没有系统色偏；差异图
  显示误差全贴在纹理边缘上。这些零件小、细节密，是高频内容遇上亚像素重采样差异，
  不是着色错误。
- **大格蕾修整体偏暗 1/255**：它的基准平均亮度 183，另两个角色只有 101。bloom 增
  益是在丽塔身上标定的，越亮的画面残差越大。0.4% 的量级，不值得再标一遍。
- **`眉毛`（三个角色都是 ΔE 11～12，约 100～150 px）**：细条上的亚像素噪声，和
  Phase 3 多视角验收时的结论一致。

#### 顺带修掉的工程问题

- `run_ref_diff.ps1` 的 `-Character` 现在直接就是模型目录名（`examples/丽塔` 已被
  用户并入 `models/特工丽塔`），PMX 文件名各角色不统一，改成自动定位：优先
  `*_修复.pmx`，否则要求目录里只有一个 `.pmx`，有歧义就列出候选让调用方指定，不猜。
- **产物曾经落到仓库外**：`Start-Process` 用的是 .NET 的当前目录，`Set-Location`
  改不到它，相对路径 `Build/RenderPreset/images/...` 于是写进了 `C:\Build`。已加
  `-WorkingDirectory`、把传给外部进程的路径全改成绝对路径，并在
  `export_blender_graph.py` 里加了一道「产物必须在仓库内，否则直接失败」的校验。

#### 结论：预处理只能是离线工具，不能内置在 App 里

这条流程依赖 **Blender 3.6**（求值几何节点得到描边外壳、导出节点图与打包贴图）和
**Unity 编辑器**（建网格、出 prefab / AssetBundle）。两个都不可能随 App 分发，所以
「选一个 .pmx + 对应的渲染预设 .blend，转换成可加载格式」必然是仓库内的离线工具，
App 只负责加载转换结果。现在的入口就是 `Tools/PmxPipeline/run_ref_diff.ps1`，
Phase 4 会把它收成一个正式的导出命令。

#### 修掉的缺陷

**1. 四个未实现的节点类型。** `VALUE` / `RGB`（常量存在**输出**插槽上，IR 之前只留
了输出插槽的类型）、`INVERT`、`COMBINE_COLOR`。

**2. 导出器从来没导出过输出插槽的默认值。** `dump_socket` 写的是
`if not is_output and hasattr(s, "default_value")`。于是 Value 节点的常量读出来是
`None`，转译时静默变成 0——灯的头顶高光因此成了一块**黑斑**（肉眼可见，用户发现
的）。现在输出插槽也导出，并且转译器拿不到常量时**直接报错**，不再退化成 0。

**3. 没复现 EEVEE 的「Show Backface」。** 关掉这个开关的材质（内部标志名
`MA_BL_HIDE_BACKFACE`），EEVEE 会加一遍**深度预通道**，每个像素只有最靠前的那层被
着色。我们照普通透明画，灯的 `长头发1` 在本该被挡住的地方透出半透明鬼影。加了
`ZWrite On / ColorMask 0 / Blend Off` 的前置 Pass 后 ΔE 5.44 → 0.85。
顺带验证过：这个标志**不是**「剔除背面」——强行 `Cull Back` 会让大月下的纱直接消失
（ΔE 14.68），已否决。

**4. 正交相机下的视线向量算错。** EEVEE 的 `cameraVec()` 在透视下返回「表面指向相机
位置」，正交下返回常量的相机朝向。基准图用的就是正交相机，画面边缘偏出约 5°。漫反射
看不出来，布林冯高光（高次幂 + 硬阈值）会被推着跑。

**5. `HASHED` 映射成了「不透明 + 直接写 alpha」。** EEVEE 的 HASHED 是**随机 alpha
测试**：放在不透明通道里，每个采样要么整个不透明要么被丢弃，最终图上的分数 alpha 完全
来自采样覆盖率。直接把 alpha 写进不透明通道，alpha≈0 的片元既不消失、又用深度挡住了
后面的层——灯-战损版的头发被打成筛子，轮廓 IoU 只有 0.9616、少了 7101 px。改成
`clip + alpha = 1` 后 IoU 0.9986。阈值用 EEVEE 的随机版
（`ME_HashedAlphaThreshold`）而不是固定 0.5：两者在 alpha 双峰的材质上逐像素等价，
但蕾耶拉的 `裙带` 用噪声驱动 alpha 做金粉溶解，固定阈值会把平滑渐变切成硬斑点。

**6. `Mix` 节点只支持 RGBA。** `FLOAT` / `VECTOR` 模式没实现，大月下 **20 个材质**因此
整个退回原材质（ΔE 26.39）。补上后 34/34、ΔE 3.01。

**7. `Noise Texture` 只支持 3D。** 补了 4D（梯度取 32 个方向、插值多一层、归一化常数
换成 `noise_scale4 = 0.8344`）。

**8. RGB Curves 的复合顺序反了。** 导出器烤的是 `cm[3](cm[ch](x))`，正确的是
`cm[ch](cm[3](x))`——先合成曲线、再逐通道曲线。本批预设的 C 曲线恰好都是恒等的，所以
修掉之后九个角色的数值一字未变；属于潜伏缺陷，实测见 `Tools/PmxPipeline/verify/`。

#### 补上的两个盲区

- **产物落到了仓库外。** `Start-Process` 用的是 .NET 的当前目录，`Set-Location` 改不
  到它，相对路径 `Build/RenderPreset/images/...` 于是写进了 C 盘根目录的 `Build`。已加
  `-WorkingDirectory`、把传给外部进程的路径全改绝对，并在 `export_blender_graph.py`
  里加了「产物必须在仓库内、否则直接失败」的校验。
- **Blender 报告没记 AO / SSR / 采样数。** 等于默认「它们是关的」，而这是没有依据的
  假设。现在一并记录（实测这批预设：`use_gtao=False`、`use_ssr=False`、
  `taa_render_samples=64`、`filter_size=1.5`）。

#### 逐点核对过的节点语义

差分数值淹没得掉的语义错误，只能单独拎出来测。装置与结论见
`Tools/PmxPipeline/verify/`：Jenkins 哈希的初始常量是 `0xdeadbeef + (n<<2) + **13**`，
Perlin 3D/4D 与 EEVEE 吻合到 1e-6（24 个采样点），RGB Curves 的顺序如上。

#### 已解决：大月下 `头巾` 与寻梦者头发（2026-10-01）

两者同源：**Image Texture 在 Alpha 输出未接线时，直通 alpha 的图输出 rgb·a**，转译器
原先直接取 rgb（探针 `verify/probe_image_alpha.py` 实测确认，见 verify README）。头巾所在
区域贴图 alpha 只有 ~0.2，未乘 alpha 让辐射偏亮——这正是当初「alpha 正确、预乘 RGB 偏高
+9/+15/+13」的现象；寻梦者头发的「高光」图 98.6% 像素 alpha=0，残留 RGB 让整片头发成了
平滑亮斑。修正后正面 ΔE：大月下 3.01→1.63（头巾 8.51→0.64），寻梦者 2.67→2.34（头发
5.83→2.15）；背面 5.51→1.85、2.38→1.68；其余七个角色逐位不变。

- **蕾耶拉 `裙带` 的金粉**：我们的颗粒比基准更多更亮。噪声与哈希已逐点验证无误，所以

### Phase 4：集成与验收（进行中）

#### 哪些能烘进离线文件，哪些必须改管线（2026-09-19 定论）

这三类东西性质完全不同，不要笼统说成「用了 MateEngine 不支持的高级特性」：

| 东西 | 能否烘进 `.me` | 说明 |
|---|---|---|
| 逐材质着色（贴图 / LUT / ramp / 法线贴图 / matcap / SDF / 程序化噪声） | **能** | 转译产物就是普通 Built-in RP 无光照着色器，不要求管线支持任何特性 |
| 描边 | **能** | 是实体化外壳，就是网格里多出来的三个子网格 |
| Filmic + High Contrast 视图变换 | **能**（逐材质做，现状即如此） | 对不透明材质数学上精确。只有两个 `BLEND` 材质（`眼睛2` / `裙内侧`）有偏差：EEVEE 在线性域合成后才做变换，逐材质做只能在显示域混合 |
| **bloom** | **不能** | 屏幕空间效果，按定义装不进模型文件 |

所以**必须改管线的只有 bloom 一项**。其余部分 App 现有管线原样就能跑。

但 bloom 值 ΔE 从 4.17 降到 1.86，正是「偏暗」与「明亮鲜艳」那个差别，不是可有可无。
而且一旦有了线性 HDR 缓冲，视图变换顺势移到末端，上面那两个 BLEND 材质的偏差也一并
消掉——改一次解决两件事。

#### 需要的三处改动

1. **3D 相机开 HDR、渲到线性缓冲**（`allowHDR` + `ARGBHalf`）。不开 HDR 的话亮部在
   1.0 被夹掉，bloom 取不到亮度——Filmic 把线性 8.0 映射到 0.993，亮部信息全在 1.0
   以上。
2. **一个 alpha 感知的全屏合成 pass**：bloom → 视图变换 → 输出。代码已就位，
   `Assets/PmxTranspileRuntime/MEPostCompose.{shader,cs}`，差分闭环里已经在用。
   着色器侧靠全局 `_MEDeferViewTransform` 切换（未设置时材质自己做变换，保证单独用
   也是对的）。
3. **把 UI 隔在合成之外。** App 只有一个主相机，它同时画角色和 Screen-Space-Camera
   的菜单画布。直接加全屏 pass 会把菜单一起变换，**正是 ADR-0010 里被用户否掉的那个
   毛病**（`RenderStyleManager.cs` 里那段 `GradeEnabled = false` 的注释记着原委）。
   两种做法：(a) 新增一个只渲 3D 内容的相机、输出到 HDR 缓冲，主相机只画 UI；
   (b) 把菜单画布改成 Screen-Space-Overlay。

> **用户 2026-09-19 已选定 A 路线**（改造管线）。理由是：不改就做不到效果一致，
> 前面的工作等于白做。

#### 辉光 alpha：本期保留原值，外圈显示后续再定

实测 Blender 的 bloom **只写 RGB、不动 alpha**：带 bloom 的基准图里轮廓外有 314456 个
像素 RGB 非零（最高 95/255），而 alpha 仍为 0；半透明像素数与不带 bloom 时完全一致
（都是 8828 个）。

分层窗口按 alpha 合成，alpha=0 的像素完全透明、RGB 不参与显示。所以**照搬 Blender
的话，轮廓外那圈辉光在 App 里是看不见的**。轮廓内（alpha=1）的辉光正常显示——「偏暗」
那件事靠的就是这部分，所以主要收益不受影响。

要让外圈辉光可见，得主动把 alpha 跟着辉光外扩（例如 `alpha = max(alpha, luma(bloom) × k)`）。
这是**有意偏离 Blender 输出**：差分数值会略变差，但 App 观感更接近用户在 Blender 里
看到的样子（Blender 图像编辑器默认按 RGB 显示、忽略 alpha，所以那边肩臂外的辉光是
看得见的）。

**2026-09-23 用户已选择本期保留原 alpha**，外圈显示留到接入后看实机再定，见 ADR-0015。

## 风险与回退

- **最大风险是量而非难度**：41 份节点组实现、712 个计算节点。对策就是转译器形态本身。
- **第二是 Filmic/look 容易被漏**，且在透明窗口约束下不能用标准全屏 tonemap 通道。对策：逐像素在片元着色器末端做。
- **第三是那 8 条残留连线**，静默读错且极难定位。对策：转译器显式按活动 `data_type` 取插槽，并对非活动插槽上的连线**报警而非忽略**。
- 丽塔的 Voronoi / Noise / bicubic 是局部精度问题，不阻塞主线，可留到后期。
- **全程保留 `materialProfile = "uts2"` 兜底**，任何改动不得破坏它。
